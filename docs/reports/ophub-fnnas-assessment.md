# ophub/fnnas 评估 —— 能不能"从上面拉飞牛系统来移植"

> 评估对象：https://github.com/ophub/fnnas
> 评估时间：2026-10-05
> 评估人：本机（Agent 取证，非推测）
> 结论一句话：**不能直接拉一份现成的 fnOS 镜像刷到 CM360（项目不含 Realtek）；但可以把它当成"fnOS rootfs 的来源 + 打包脚本的现成参考"来用，真正的门槛是内核版本（6.12/6.18 vs 我们的 6.6.54）。**

---

## 一、这个项目到底是什么

ophub/fnnas 是 ophub（amlogic-s9xxx-armbian 系列作者）做的一套**重打包框架**，不是飞牛官方项目。
它干的事情是：

1. 拿 **飞牛官方 arm64 镜像**（`.img`，存在 `fnnas_base_image` release 里）当基础包；
2. 把 **ophub 自己重编的内核**（`kernel_fnnas` release，从官方 `.deb` 重打包）替换进去；
3. 按目标盒子的 dtb / u-boot 分区布局重新组装，产出一个"可以 `dd` 到 TF 卡或写进 eMMC"的镜像。

脚本清单（都在仓库根目录）：

| 脚本 | 作用 |
| --- | --- |
| `renas` | 本地打包：官方镜像 + 指定内核 + 指定板子 → 可刷镜像 |
| `rekernel` | 重装内核：改镜像里的内核/dtb，或装官方 `.deb` |
| `fnnas-install` | 把当前系统装进 eMMC |
| `fnnas-update` | 在线升级内核（自动备份最近 3 个版本，`-s` 可 SOS 回滚） |
| `fnnas-swap` / `fnnas-ddbr` | 换 swap / 备份恢复 |
| `fnnas-sync` | 同步最新服务脚本 |

这一点很关键：**它的产物是"飞牛官方 rootfs + ophub 内核 + 各家 dtb"的三明治**。所以"拉飞牛系统"这个诉求，本质上是拉那层 rootfs。

---

## 二、支持列表里没有 Realtek —— 硬事实

README 的设备表（实测抓取，共 27 行板卡条目）覆盖：

- **Amlogic**：a311d / s922x / s905x3 / s905x2 / s905l3a / s905l3b / s905l3 / s912 / s905d / s905x / s905mb / s905l / s905l2 / s905lb / s905w / s905
- **Rockchip**：rk3588(s) / rk3576 / rk3399 / rk3568 / rk3566 / rk3528 / rk3328 / rk3318
- **Allwinner**：h618 / h6

**Realtek 一次都没出现**，也没有任何 RTD129x/RTD1296 条目。`model_database.conf` 的 `BOARD` 列表同理，全是三家的代号（`s905x3`、`rk3588`、`h618` 这种）。

→ **没有 CM360 可直接用的镜像**。它 Releases 里 6 个 `fnnas-official-arm64-image_*.img.xz`（各 ~1.7 GB）全部按"平台_内核系列"切分，是给这三家的板子用的，分区布局（u-boot 位置、dtb 位置、GPT 表）都是照着 Amlogic/RK/AW 的约定做的，跟 RTD1296 完全不同。

---

## 三、内核版本：这里是真正的坎

`kernel_fnnas` release 里**只有 6 个内核包**（实测）：

```
6.12.41-allwinner.tar.gz      92.72 MB
6.12.41-amlogic.tar.gz       110.57 MB
6.12.41-rockchip.tar.gz      104.46 MB
6.18.18-amlogic.tar.gz       136.38 MB
6.18.18-rockchip.tar.gz      105.38 MB
6.18.6-allwinner.tar.gz      110.37 MB
```

也就是说 **fnOS 生态目前只有 6.12.y 和 6.18.y 两档内核**，默认 `6.18.y`。
而我们的内核是 XpressReal/linux **6.6.54**。

这会产生三个层次的问题：

1. **驱动 ABI 层**：我们的 RTD1296 驱动（`rtkemmc.c`、`dw_mmc_cqe-rtk.c`、`irq-realtek-mux.c`、`phy-rtk-sata.c`、`clk-rtd1295-cc.c`、SMP 的 `smp_spin_table.c` 改动）全部是在 **6.6.54** 上验证通过的。6.12/6.18 的 mmc 核心、gpiolib、irqchip、clk 框架都有演进，直接拿过去编**大概率要重新调**。
2. **fnOS 用户态/libc 假设**：fnOS 是 Debian 系深度定制，它的内核模块（`.ko`）是按 6.12/6.18 编的。如果系统里有任何**预编译内核模块**（比如它自带的文件系统/网络加速模块），换 6.6 内核后会因为 `vermagic` 不匹配而全部加载失败。
3. **官方校验**：README 里 `fnnas-update -k 6.18.18` 这种用法说明**系统层是按内核版本号来管理升级的**。是否在启动时对内核版本做硬校验（拒绝 6.6），README 没有说明 —— **这是我目前无法从纸面证实的唯一关键未知项**。

## 四、那么能做的是什么 —— 三条路线

### 路线 A：反向移植驱动到 6.12/6.18（正统，工作量大）

把我们在 6.6 上跑通的 RTD1296 驱动，搬到 6.12 或 6.18 内核树里重编。

- **优势**：内核版本完全对上 fnOS 要求，用户态模块零冲突，`fnnas-update` 之类的官方工具都能正常工作。
- **依据**：驱动本身是开源的，而且已经有**第三方在同 SoC 上做过新版内核**——`jjm2473/rtd1295-next` 就是 Linux 5.9 的 RTD1295/1296 移植树（我们的 `rtkemmc.c` 正是从它那里来的）。往上再抬到 6.12 是有前人路径的。
- **代价**：mmc 核心在这几个版本之间改动不小（`mmc_select_timing`、`card_type` 选择逻辑），`rtkemmc.c` 那些依赖 `#ifdef CONFIG_ARCH_RTD129x` 的分支**每一处都要重新过一遍编译**（参考我们踩过的坑：`#ifdef` 里的代码"有人写过"≠"编译过"）。
- **预估**：这是几个星期的活，不是几天。

### 路线 B：6.6.54 强上（快，但赌官方校验）

保留我们现在**已经完全打通**的 6.6.54，只把 fnOS 的 rootfs 抽出来换上。

- **做法**：取一份 `fnnas-official-arm64-image_*.img.xz`（比如 rockchip 1253 那份），解包出 rootfs 分区，把我们的 `Image-6.6` + `rtd1296-cm360.dtb` + initramfs 塞进去，按 CM360 的分区布局重做镜像。
- **风险**：如果 fnOS 启动时对内核版本有硬校验，会直接拒绝启动；即使不校验，任何预编译内核模块也会失效。
- **成本**：几天，而且**能立刻验证那个关键未知项**——这本身就是价值。

### 路线 C：先解剖镜像（零风险的信息收集）

**不刷机**，只下载一份官方镜像，把它的结构看清楚：

1. 分区表（GPT）里有几个分区、各自布局、`bootfs`/`rootfs` 各自多大、有没有独立的 kernel 分区；
2. rootfs 里 `/boot` 下有没有现成内核、`vermagic` 是什么；
3. 有没有 `btrfs` / overlay 相关工具（fnOS 的存储特性）；
4. 有没有对内核版本做检查的脚本（`/etc/initramfs`、`/usr/lib/fnnas` 之类）；
5. 有没有预编译 `.ko`，依赖的内核版本。

**这条路线唯一要花的成本是 ~1.7 GB 下载 + 解包时间**，但能把路线 A 和 B 的取舍从"猜"变成"知道"。
**建议先走这条。**

---

## 五、我的建议

**先做路线 C，然后按它的发现决定 A 还是 B。**

理由：
- 路线 C 是纯信息收集，不改任何东西、不刷任何机，**风险为零**；
- 它回答的正是当前最关键的未知项（fnOS 对内核版本的真实态度），而这个答案直接决定后面几条路值不值得走；
- 如果发现 fnOS 对内核版本是"软依赖"（只影响某些可选模块），那么路线 B 几天就能出成果，可以直接把 CM360 点亮成飞牛 NAS；
- 如果发现是硬校验，那就早点知道，把资源集中到路线 A 的反向移植上，不要浪费时间在 B 上试。

**顺带可以做的事**：把 `fnnas` 仓库 clone 下来，`renas` / `rekernel` / `fnnas-install` 这几个脚本读一遍。它们处理分区、生成 initramfs、写 eMMC 的那些逻辑，跟我们 CM360 要写的安装器是同类问题，很值得抄思路 —— 尤其是 `fnnas-install` 怎么写 eMMC 引导。

---

## 六、一句话总结

> **不能"从 ophub/fnnas 拉一份现成飞牛系统刷到 CM360"（它不支持 Realtek、也没有 RTD1296 镜像）。**
> **但可以"从它那里拿飞牛官方 rootfs，配我们自己的内核"。**
> **拦路虎是内核版本：fnOS 要 6.12/6.18，我们是 6.6.54。**
> **先解剖一份官方镜像确认 fnOS 对内核的真实要求，再决定是"6.6 强上"还是"驱动反向移植到 6.12"。**
